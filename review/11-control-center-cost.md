## 0. 结论先行（TL;DR）

| # | 结论 | 一句话 |
|---|---|---|
| **1** | **不做 1:1 复刻** | DSH Dock 是 **63,230 行代码**（Rust 33,952 + TS/TSX 29,278）+ 18,529 行文档、**22 个发行版 / 约 6 周**密集迭代的**独立桌面应用**。用插件复刻它，等于在一个"寄居在别人 App 里的脚本"里重造一个桌面 App —— 不划算的边界就在那里，不是"要不要努力"的问题。 |
| **2** | **值得做，但先从最小可用版的一半开始** | **先做 M0+M1 = 12~17 轮 / 1~2 天**（玻璃外壳 + 工作区管理）；完整最小可用版 **M0+M1+M2 = 20~27 轮 / 2~3 天**（加会话巡检，**只读优先**）。 |
| **3** | **M3 插件管理"卡在门口"** | 官方 `pluginManager` 的启停/装卸接口已齐全（`listPlugins / setPluginEnabled / installBundle / removeBundle` 等，全部 `@Remote`），**但"停用插件 → DSH 起不来"是你已知的坑②**。做它之前必须先有 M5 安全模式，所以 M3 不能单独上。 |
| **4** | **三件事坚决不做** | ① **不自己存凭据**（走官方 `credentialsController`，自己存 = 明文密码风险）；② **不自动改会话文件**（写坏 = 丢对话，不可逆）；③ **不自建插件市场**（3400+ 条目的数据源不在我们手里，且社区已有现成的 `dsh-market`）。 |
| **5** | **维护成本分水岭在 70%** | 最小版在 DSH 升级后**多数时候不用改**（不改 profile 文件、不碰会话文件）；70% 档**每次升级都要重测**；1:1 档是"每次 DSH 升级 = 重走一遍 6 周"。 |
| **6** | **最大白做风险不是写不出来，是"写出来不用"** | 你现在用的是**双击 .bat 启动的 DSH**，而控制中心的价值 80% 在"出事时救命"（插件冲突、会话异常、安全模式）。如果你平时不出事，它会变成一个"打开看过两次就再没打开"的面板。**这一点必须由你本人拍板。** |

**一句话推荐**：**先做 M0（玻璃外壳）＋ M1（工作区管理），做完就用一周。** 一周后你还想打开它 → 继续做 M2（会话巡检）；一周后你自己都忘了它在哪 → 停手，省下的全是净赚。

## 1. 估算基准与口径（凭什么这么算）

### 1.1 「一轮」是什么，值多少

| 项 | 定义 | 依据 |
|---|---|---|
| **1 轮 AI 协作** | 一次对话往返 =「我提需求 + AI 改代码 + 跑验证 + 我看结果」 | 用户既定习惯 |
| **1 轮实际产出** | 约 **600~900 行**可验收的新代码（含验证脚本），或 **3~5 个界面功能项** | 本项目 `client.js` 4483 行 + `index.js` 929 行 + 验证台，跨约 20+ 轮 |
| **1 轮墙钟时间（顺利）** | 20~40 分钟 | 本项目的实际节奏 |
| **1 轮墙钟时间（含排障）** | **乘 1.5~2.5 倍**（30~90 分钟） | 见 1.2 的"难查故障"锚点 |
| **一天能跑几轮** | 6~10 轮（有完整验收脚本时）；3~5 轮（纯疑难排障时） | 依据本项目 09-11/09-12 那种密集排障日的节奏 |

### 1.2 五个真实锚点（这是本报告所有估算的来源）

**锚点 A —— 本项目自己：UI 框架一轮就成，但"修 bug"要 3 倍时间**

| 事实 | 数据 | 对估算的意义 |
|---|---|---|
| 玻璃材质 + 壁纸画廊 + 可拖动控件 + 找回圆点 | 已交付，约 4400 行 `client.js` + 415 行 `styles.css` | **新建 UI 的产能基线**：复杂界面组件 ≈ 1 轮 / 组 |
| 「左栏行级玻璃 + 蓝色品牌 + 输入栏玻璃」这一组改动 | 跨 1 轮，验收 `collapse.test.mjs` **12/12 PASS** | **加一组界面增强 ≈ 1 轮** |
| 设置面板（6~7 个设置项） | 跨 2~3 轮，`settings.test.mjs` **16/16 PASS** | **1 轮 ≈ 3 个设置项（含持久化 + 即时生效）** |
| 架构审查找出 **P0×1 / P1×4 / P2×16** | 单轮（独立审查会话） | **一轮审查能挖出 21 个问题** → 问题密度极高 |
| 修复代价 | 21 条里绝大多数是 **1~5 行补丁**（P1-1 补 3 行、P2-9 删 4 行） | **写代码便宜，找问题贵** |
| 8 类历史坑（激活失败 / 配置撞名 / 跨作用域 ReferenceError / 静默插入失败 / `backdrop-filter` 包含块 / 全屏模糊闪烁 / 玻璃预算误伤 / 点击抑制吞点击） | 每一类都是"看起来没生效" | **每类平均排查 1~3 轮**，且症状与原因距离极远 |

> **锚点 B 的用法（本报告最重要的一段）**：一个有 30 篇 ADR、有机器闸门、有独立验证报告、迭代了 22 个版本、**写掉 63,230 行代码（33,952 行 Rust + 29,278 行 TS/TSX）**的成熟项目，**仍然把一个平台的核心操作（窗口移动/缩放/关闭）做坏了，而它自己的测试是绿的**。这直接决定了本报告的两条结论：
> ① **1:1 复刻不划算**不是"我们能力不够"，而是**那个量级的系统（6.3 万行代码）在工程上被证明会反复翻车** —— 而且它的 6.3 万行还是**一个人写不完的量级**：DSH Dock 有完整的 AI 协作团队编制（`docs/team/README.md`）与 57 篇治理文档，仍然如此；
> ② **凡是要碰系统级能力的功能（窗口、进程、端口、更新、凭据），必须先有"自动回滚/安全模式"再造功能** —— 否则一次失败就是"整个界面坏掉"，而不是"降级显示"。

**锚点 C —— DSH 的官方 API 比想象的多（这决定了"最小版"能有多便宜）**

我通过 Cordis Inspect 读到了本机 **活的 Host 服务目录**，以下接口**全部已存在、可被插件调用**（不是推测）：

| 控制中心想要的 | DSH 已有的官方接口 | 结论 |
|---|---|---|
| ① 工作区管理 | `workspaceRegistry`：`create / list / get / delete / insertBefore / archiveSession / unarchiveSession / pinSession / unpinSession / resolveByPath`；`workspaceController`：`create / rename / delete / insertBefore / insertSessionBefore / archiveSession / pinSession / follow`（`@Remote` 流式 follow） | **数据层 100% 现成**，只剩 UI。**注意（Lead 校正）**：要对齐的是 **DSH Workspace**，不是 DSH profile —— 见下方说明 |
| ② 插件管理 / 市场 | `pluginManager`：`listPlugins / listBundles / registries / inspect / setPluginEnabled / setBundleEnabled / installBundle / removeBundle / waitForInstall / cancelInstall`（**全部 `@Remote`，即前端可直接调**）；`pluginRegistryProbe.fastest()`（官方在选最快的 registry） | **API 全齐**；"3400+ 条目"这个**数据源**不在官方接口里，那才是难点 |
| ③ 会话健康巡检 | `sessionController.inspect(sessionId)`（**官方巡检入口**）、`sessionController.list / search`、`sessionPersistence.list / stat`（**只读快照**） | **巡检是"读"，官方全给了**；"自愈"是"写"，官方没给 |
| ④ 凭据 | `credentialsController`：`describe / set / unset`（`@Remote`）；`credentials`：`resolve / describe / set / unset / listRecords / modifyRecord / deleteRecord` | **安全红线不用自己扛** |
| ⑤ MCP 配置 | `configEditor`：`entries / configuration / edit(entry, change)`（走正常 Loader 路径持久化） | **写入有官方通道**，但见 §4 风险 |
| ⑥ 诊断 / 日志 / 版本 | `sessionPersistence.stat`、`hmr`、`clientModules.graph / onGraphChanged`；DSH 版本由壳/宿主提供 | 读得到 |
| ⑦ **控制中心自己的 API 面** | **`webServer.register(route)`**（`webServer` = "The browser HTTP carrier service"，另有 `registerUpgrade / registerFallback / tapIndex / collectIndexInjections / renderIndex`） | **★ 不必新开端口**：把控制中心的 API 注册进 **DSH 自己的同源 web server**，一次性绕开端口发现、CORS、`ACAO:*` 与 token 传输 —— **同源策略本身就是栅栏**。这比"自己起一个 3932x 服务再加 token 鉴权"干净得多，也顺手还掉了 `review/01-architecture.md` P2-14 那笔 CORS 全开的债 |

> **Lead 校正的两条（已并入上表与 §3.3）**
> 1. **不需要动 39321-39324 端口**：实测 DSH 宿主暴露 `ctx.webServer.register(route)`。控制中心的服务面**注册到 DSH 自己的 web server 上、同源访问**即可 —— 这是本报告推荐的做法（本报告从未建议给自建端口加 token 鉴权；如果你在别处看到那个方案，用本条替换）。
> 2. **"多工作区管理"要对齐 DSH Workspace，不是 DSH profile**：`workspaceRegistry` / `workspaceController` 才是官方 API。DSH Dock 那套「一个 profile 一个 DSH 进程」是 **Tauri 壳 spawn 子进程**的形态（`docs/contract.md:65-74`：`node <dshBinJs> --profile <profile> --port 0`，环境注入 `DSH_HOME`），**插件在已经启动的 DSH 内部做不到** —— 它不能换掉自己脚下的那个进程。**这进一步坐实了 §3.3 的硬线一（绕过 DSH 插件加载器的能力）**：M1 的"切工作区"是**在同一个 DSH 进程内切换 Workspace**，而 DSH Dock 的"切 profile"是**杀掉一个 DSH 进程再起另一个**。两者同名不同物，别把后者的期待搬到前者上。

> **锚点 C 的用法**：控制中心**不是**"从零造一个 DSH Dock"，而是"**把 DSH 已有的 7 组官方接口（含 `webServer.register` 这一组同源服务面），用你插件的玻璃质感包一层 UI**"。这直接把最小版的成本压到个位数天，也**同时解释了为什么 70% 以上不划算** —— 超过那 7 组的东西（进程生死/自更新/系统托盘/跨平台壳）官方接口里没有，得自己造，而那正是 DSH Dock 花了 **63,230 行代码 + 6 周、并且在 Windows 上翻车**的地方。

**锚点 D —— 用户侧的真实约束（决定"值不值"）**

| 约束 | 事实 | 影响 |
|---|---|---|
| 启动方式 | 双击 `.bat` / 双击 DSH 快捷方式 | 控制中心必须"界面内可达"，不能要求开终端 |
| 第三方方案 | DSH Dock 启动即崩（`0xc0000409`，故障模块是它自己的 exe，**两次同一偏移**） | **这不是配置问题**：`0xc0000409` 是 Windows 的 `STATUS_STACK_BUFFER_OVERRUN`，Tauri 应用上最常见的一个成因是 **WebView2 运行时初始化失败**（需真机确认，本报告不把它当定论）。**但结论不依赖根因**：一个"启动即崩"的第三方控制中心，在你这台机器上已经是零可用性 —— 不可能成为方案 C 的替代品，只能成为"我们该不该自己做"的动机 |
| 现有插件的健康度 | 架构审查 P0×1/P1×4/P2×16；体验审查 **P0×5**（其中「亮壁纸读不了字」对比度 **1.41:1**、`prefers-reduced-transparency` 会变成**白底白字**） | **动手做控制中心之前，这 6 个 P0 更该先修** —— 见 §5.3 |

**锚点 E —— 契约稳定性（决定维护成本的关键一手依据）**

DSH Dock 的 `docs/contract.md` 给了一个**反面样本**：它的运行契约是 `product.manifest.json` 里的 `format: 1`，并且写明「**不匹配 → 壳拒绝启动（错误页提示重新打包）**」，契约改动流程要求「本文件先改 → `format` 升版本 → 壳 `MANIFEST_FORMAT` 同步 → 打包侧同步 → **三步用同一版本号发布，缺一不可**」；它的产物还是**冻结快照**（「桌面版是冻结快照（ADR-0004 D4）：产物不可变；用户升级 = 回装配车间重打一版」）。

> **用法**：这是一个**强版本耦合**的契约 —— 每次上游格式变，它就要动三个地方并重新打包。**与之相对，我们插件侧用的是 DSH 的 `data-*` 钩子 + `--dsw-*` 令牌 + 服务名**（比 `format` 版本号稳），所以我们的维护成本天然低于 1:1 档。**但代价是**：钩子坏了**不报错、不崩溃，只是"看起来没生效"**（`review/03-release.md` §6.3 列的 7 个失效点、以及已踩过的 8 类坑）。**这就是维护成本的形状：不是"每次升级都大修"，而是"每次升级都要跑一次诊断、有一次可能要花半天找一处改名"。**

### 1.3 三档的公共前提（一次投入，三档都省）

| 前提 | 说明 | 成本 |
|---|---|---|
| **P-1 先有回滚** | 控制中心上线前，`git tag` 打点 + 一键恢复脚本（不能只靠 `D:\dev-cache\temp` 本机备份 —— `review/03-release.md` R-10 已指出这条对外不可执行） | 1~2 轮 |
| **P-2 先有诊断** | 复用已有的 `test\诊断-双击运行.bat` + `diagnose.mjs`，新增"控制中心"段的探针 | 1 轮 |
| **P-3 先跑通"不生效"三类判据** | `scriptLoaded / factoryRuns / applyDone` 三行组合能区分"文件没送到 / factory 没跑 / apply 没跑"（README 与 `03-release.md` §6.1 已有现成范式） | 已存在 |
| **P-4 不写别人的文件** | **控制中心第一版只读 profile 与 sessions，不改** | 0（设计选择） |

## 2. 里程碑与工时（6 个）

> 每个里程碑都是**可独立交付**的（做完就能用、能验收、能停）。轮次为**估算区间**；墙钟时间按 **1 轮 ≈ 30~60 分钟**（含验证与排障）折算，并给出"顺利 / 不顺"两端的说明。

### M0 · 玻璃控制中心外壳（**必做**）

| 项 | 内容 |

### 3.2 为什么"70%"这个档名其实有点骗人

**它的功能是 DSH Dock 的 70%，代码量是 12~20%，但"风险"是 80~90%。**

原因：那三块最贵的功能（插件启停、MCP 写入、安全模式）**恰好都是"能改坏环境"的功能**。它们的代码量小（官方 API 接线），但每一次失败都指向"DSH 起不来"。所以第 ② 档的特点不是"贵"，而是：

> **它的成本不在写代码，而在"每次改都要先想好怎么救回来"，以及出事之后的那 3~5 轮排障。**

### 3.3 复刻不划算的边界在哪（**明确回答**）

**边界不是百分比，是两条硬线。** 越过任一条，1:1 复刻就不划算：

**硬线一：需要"绕过 DSH 的插件加载器"的功能 —— 越过即不划算**

DSH 插件是**寄居**在 DSH 里的（客户端半体必须是包根的 `client.js`、走 `window.__ModuleLoader__`、宿主半体与主进程同进程）。凡是"DSH 自己已经坏了才需要"的能力（安全模式救人、更新自身、切换 DSH 版本、接管进程与端口），**插件在定义上就做不干净** —— 它需要 DSH 先能跑起来。DSH Dock 之所以做成独立 Tauri 应用，正是因为它要管 DSH 的**生与死**：它的 `docs/contract.md:65-74` 写得很清楚 —— 壳自己 spawn `node <dshBinJs> --profile <profile> --port 0` 并注入 `DSH_HOME`，**一个 profile 对应一个由它启动的 DSH 进程**。插件在已经启动的 DSH 内部，**换不掉自己脚下的那个进程**。**这不是工程量问题，是架构位置问题。**
>
> **这条硬线有一个立刻要澄清的实用推论（Lead 校正）**：M1 做的"切工作区"，切的是 **DSH Workspace（同一进程内的工作区）**，走官方 `workspaceRegistry`；**不是** DSH Dock 那种"换一个 profile = 换一个 DSH 进程"。**别把后者的期待搬到前者上** —— 如果你要的是"同时开好几个互不干扰的 DSH（各自的插件、各自的凭据）"，那属于硬线一之外，插件做不到，只有独立壳能做。

**硬线二：需要"系统级能力"的功能 —— 越过即不划算，且有实测证据**

窗口拖拽/缩放/关闭、托盘、进程生命周期、跨平台壳、自更新验签 —— 这些是 DSH Dock 花了 6 周并且在 Windows 上**真坏过**的地方（锚点 B 的逐字记录：三条独立根因叠加，且它自己的闸门是绿的）。我们用插件做这些**没有一项能比它做得更好**，只会更差。

**边界的具体刻度（可直接用）**：

| 若你想做的是… | 在不在边界内 | 怎么做 |
|---|---|---|
| 工作区列表与增删改（**同一 DSH 进程内的 Workspace**） | **内** ✅ | 官方 `workspaceRegistry` / `workspaceController`，只做 UI |
| 「同时开多个互不干扰的 DSH（各自插件/凭据）」= 换 profile 进程 | **外** ❌ | 这是 DSH Dock 的形态（壳 spawn `--profile <p>` 子进程）。插件在**已启动的** DSH 内部做不到 |
| 会话健康巡检（只读） | **内** ✅ | 官方 `sessionController.inspect` |
| 控制中心自己的 API 面 | **内** ✅（**推荐做法**） | `webServer.register(route)` 注册到 **DSH 同源 web server** —— **不新开端口、不需要 CORS、不需要 token** |
| 已装插件的启停 | **边界上** ⚠️ | 官方 API 有，但**必须先有安全模式** |
| 社区插件市场（3400+） | **外** ❌ | 数据源不在官方接口里；社区已有 `dsh-market`；**重造没有意义** |
| 凭据的**展示与写入** | **外**（写入）❌ | 展示走官方 `credentialsController`；**写入一律引导到 DSH 自带界面** |
| 会话"自愈"（自动改会话文件） | **外（红线）** ❌ | 只做"提示 + 可逆动作"（归档 / 清临时文件） |
| 系统和控制台 / 日志 / 端口 | **外** ❌ | 这些是独立应用才能做的（DSH Dock `updates.rs` **2008 行**、`engines.rs` **2414 行**、`network_gate.rs` **1042 行** 就是这块） |
| 更新 DSH 版本 / 自更新 | **外** ❌ | 需要独立进程与验签（DSH Dock 有一整套 Ed25519 + blake2b-512 验签与镜像链，`updater.rs` **1036 行**） |
| 独立窗口 / 托盘 / 沉浸式标题栏 | **外** ❌ | **已经在 Windows 上被 DSH Dock 证伪过**（三条独立根因叠加） |

> **一句话**：**"用 DSH 的官方接口 + 我们的玻璃 UI" 划算；"重造 DSH 的周边生态"不划算。** 边界就画在官方接口的边上 —— 这也是最小版能只用 2~3 天的根本原因。

### 3.4 三档的"每块钱买到了什么"（可比性收口）

| | ① 核心最小版 | ② 70% | ③ 1:1 |
|---|---|---|---|
| 你每天会打开吗 | **会**（工作区切换是高频动作） | 偶尔（启停插件/查日志是低频） | 不太会（独立再开一个 App） |

| 坏了会怎样 | 面板打不开 | DSH 可能起不来（有 M5 兜底） | 整个应用不可用 |
| 单位轮次的价值 | **最高**（≈1.5 块能力 / 23 轮） | 中（≈2.6 块 / 54 轮） | **最低**（4 块 / 180 轮，且要换栈重写） |

## 4. 维护成本（DSH 每次升级后的返工量）

> **口径**：一次 DSH 大版本升级（DOM/API/令牌有变动）。返工量 = "跑诊断 + 定位 + 改 + 回归"的总轮次。依据是两个已经发生过的事实：本项目**已踩过 8 类坑**（每类都是"看起来没生效"），以及 `review/03-release.md` §6.3 列出的**7 个最可能失效点**。

### 4.1 各档返工量

| 档 | 每次 DSH 升级的返工 | 依据 |
|---|---|---|
| **① 核心最小版** | **0~2 轮 / 次**（≈0.5~2 小时） | 只依赖三类稳定信息：DSH 的 `data-*` 钩子、CSS Modules 类名**后缀**、`--dsw-*` 令牌（`03-release.md` §6.2 已列全表）；且**不改 profile 文件、不碰会话文件**，所以官方改了文件格式也与它无关。多数升级只需跑一遍 `check-install.mjs` + `collapse.test.mjs` + `settings.test.mjs` 确认全绿 |
| **② 70% 档** | **3~8 轮 / 次**（≈2~6 小时） | 多出三类敏感面：① `pluginManager` 接口（**坏了是静默的** —— 你已知的坑②形态：插件不在 bundle 列表时 DSH 不报错、不崩、样式完全不出现）；② profile 文件格式（`profileContext.startedBundles` / `overlays` / `packageManager` 任一改名都要跟着改）；③ 社区 registry（**我们控制不了**）。另外每次升级都要**重跑"启停插件"的破坏性演练**，这才是主要成本 |
| **③ 1:1 复刻** | **每次升级 = 重走一遍 6 周**（不是夸张：它连自己的产物都是**冻结快照**，"用户升级 = 回装配车间重打一版"） | `docs/contract.md` 的 `format: 1` 三条同步发版 + 冻结快照语义；再加跨平台/浏览器/系统依赖（WebView2、`libayatana-appindicator3`、Windows 未签名、ARM64 仿真 —— 这些都在它的 v1.3.x 说明里） |

### 4.2 「不修会怎样」—— 降级显示 or 整个界面坏掉（分档回答）

| 档 | 大多数情况 | 最坏情况 | 具体表现 |
|---|---|---|---|
| **① 核心最小版** | **降级显示** | 面板的**某一块**消失，主界面不受影响 | ① 钩子改名 → 面板照常开，但工作区列表空 → **我们会写成"取不到工作区列表（DSH 接口可能改名）"，不是空白**；② 令牌改名 → 玻璃发灰/发白（现在有主题探测 + 兜底 alpha，"颜色不对"而不是"没效果"）；③ 极端：面板入口按钮定位失效 → 面板打不开，但 **DSH 本身一切正常**，删插件即回原样 |
| **② 70% 档** | 多数是**降级**（列表空、开关点了没反应） | **两级最坏**：<br>**A. 插件管理静默失效** —— 插件没被登记 → 不报错、不崩、**界面完全不出现**（坑②的原始形态，排查很贵）<br>**B. 启停写坏 profile → DSH 起不来** → **整个界面坏掉**（此时唯一救济是 M5 安全模式或手工改回 profile） |
| **③ 1:1 复刻** | **整个界面坏掉** | **启动即崩** | 这不是推演：DSH Dock 已经发生了两次 —— ① 在**你的机器上** `0xc0000409` 启动即崩（故障模块是它自己的 exe、两次同一偏移）；② v1.3.2 让 Windows 窗口**既不能移动、也不能缩放和关闭**。它自己的总结最值得抄下来：**"此前的闸门只断言脚本里出现过方法名，授权缺失或机制失效时测试照样绿"** |

### 4.3 降低维护成本的四条具体做法（第一版就要做进去）

| # | 做法 | 收益 | 依据 |
|---|---|---|---|
| **1** | **只读优先**：任何"改 DSH 状态"的功能都先做成只读版 | 把最贵的一类返工（静默失败）从根上避开 | 本项目坑②/④（激活失败、静默插入） |
| **2** | **契约面收窄**：只用 `data-*` 钩子 + 类名后缀 + `--dsw-*` 令牌 + 官方服务名，**永不写构建后哈希类名、永不硬编码路径** | 升级后多数时候"不用改" | `03-release.md` §6.2 三类稳定信息；`README` 交付自检第 2 项 |
| **3** | **升级当天跑一遍三条命令**：`check-install.mjs` → `collapse.test.mjs` → `settings.test.mjs`（+ 新增控制中心的巡检用例） | 把"半天找一处改名"变成"10 分钟定位到哪一类" | `03-release.md` §6.1/§6.4；`README` 第九节第 3 条 |
| **4** | **诊断自动脱敏**（`--redact` 默认开） | 避免又一份"含真实会话标题"的 JSON 落盘（已在 `review/03-release.md` R-02 被列为 P0） | `03-release.md` §1.3 |

## 6. 推荐决策（明确、不骑墙）

### 6.1 一句话推荐

> **做，但只做 M0 + M1（玻璃外壳 + 工作区管理），约 12~17 轮 / 1~2 天；做完用一周再决定要不要 M2。1:1 复刻明确不做。**

### 6.2 明确的分档判断（不含糊）

| 对象 | 判断 | 理由（一句） |
|---|---|---|
| **1:1 复刻 DSH Dock** | ❌ **不做** | 它是 **63,230 行代码** / 22 版 / 6 周的独立桌面应用，靠"能管 DSH 生死"（自己 spawn `--profile` 子进程）和系统级能力立足；插件架构**在位置上**就做不了这两类事，而且它在 Windows 上真坏过两次 |
| **DSH Dock 的 70%** | ⚠️ **暂不做**，等 M5 安全模式 + 一周观察期后再定 | 那三块新增能力（插件启停 / MCP 写入 / 安全模式）恰好都是"能改坏环境"的，成本不在代码而在每次动手前的回滚准备 |
| **核心最小版（M0+M1+M2）** | ✅ **做** | 官方 API 把数据层全包了（`workspaceRegistry` / `sessionController.inspect`），我们只写 UI；坏了大不了"面板打不开"，**可回滚** |
| **最小可用版再砍一半（M0+M1）** | ✅✅ **最推荐先做这个** | 12~17 轮 / 1~2 天，买的是**高频动作**（工作区切换），且**不含任何不可逆操作** |
| **会话"自愈"（自动改会话文件）** | ❌ **不做** | 写坏 = 丢对话，不可逆，且官方 append-only 接口没有"删改"语义 |
| **自建插件市场（3400+）** | ❌ **不做** | 数据源不在我们手里，社区已有 `dsh-market` |
| **自己存凭据** | ❌ **不做** | 安全红线；官方 `credentialsController` 已够用 |
| **先修现有 6 个 P0** | ✅ **必须先做** | 控制中心是"门面"，门面建在"亮壁纸读不了字 / 白底白字"的地基上，打开一次就不会再打开 |

### 6.3 「最小可用版」的精确定义（照着做就行）

**范围（三件事，不多做）**

1. **玻璃控制中心外壳**：可开可关的抽屉；3 个分页；关闭三通道（按钮 / `Esc` / 点外部）；宿主不在时给人话提示；分页崩了不拖垮整页。**新增服务面一律走 `webServer.register` 同源注册**（不新开端口、不加 CORS）。
2. **工作区管理**：列表 + 新建 / 重命名 / 排序 / 归档 / 置顶 + 一键切换（**同一 DSH 进程内的 Workspace**，走官方 `workspaceRegistry`）。**删除先不做**（只做归档）。
3. **不做**：插件启停、MCP 写入、凭据写入、会话自愈、市场、独立窗口、托盘、更新、**换 profile 进程**。

**时间**

| 里程碑 | 轮次 | 墙钟 |
|---|---|---|
| 前置：先修 6 个 P0（`02-ux.md` P0×5 + `01-architecture.md` P0-1） | 4~6 轮 | 2~4 小时 |
| M0 玻璃外壳 | 6~8 轮 | 3~5 小时 |
| M1 工作区管理 | 6~9 轮 | 3~5 小时 |
| 真机回归 + 回滚演练 | 2~3 轮 | 1~2 小时 |
| **合计** | **18~26 轮** | **9~16 小时 → 按 6~8 轮/天 ≈ 1.5~2.5 天** |

**第一版可用的判定标准（4 条，全绿才算交付）**

1. 面板能开能关，三条关闭路径都灵，关后主界面 100% 恢复原状（无 `data-dshlg-*` 残留）。
2. 在控制中心里**新建一个工作区 → 切过去 → 重命名 → 归档 → 置顶**，五步做完，**去 DSH 自带界面核对一致**。
3. **故意把宿主服务停掉**再打开面板 → 显示人话提示，主界面不受影响。
4. **一键回滚可用**（`git tag` + 恢复脚本，不依赖 `D:\dev-cache\temp` 本机备份 —— 那是 `03-release.md` R-10 的债）。

**一周观察期判据（决定要不要继续）**

> 一周内你**主动打开控制中心 ≥ 5 次**（不是"为了测试"，是真的想用）→ 继续做 M2（会话巡检，6~10 轮）。
> 一周内打开 ≤ 2 次 → **停手**，把已有成果当"顺手做的小工具"留着，把时间还给标定工作。**省下的 8~20 轮就是这次评估最大的产出。**

## 7. 对比第三方（DSH Dock / DSH 自带设置页）—— 本方案的价值点到底在哪

### 7.1 三方对比（同一张表，逐项可比）

| 维度 | **DSH Dock（第三方，成熟）** | **DSH 自带设置页** | **本方案（方案 C：做进玻璃插件）** |
|---|---|---|---|
| 现状 | **在你的机器上启动即崩**（`0xc0000409`，故障模块是它自己的 exe，两次同一偏移） | 能跑，官方维护 | 还不存在（本评估的对象） |
| 功能面 | **4/4 块全有**（工作区 / 3400+ 市场 / 巡检自愈 / 系统控制台），含独立窗口、托盘、自更新验签、WSL 客体档、多平台；代码量 **63,230 行**（Rust 33,952 + TS/TSX 29,278）+ 18,529 行文档 | 基础设置（模型、凭据、MCP、插件开关等官方已有的部分） | 最多 2.6/4 块，且**只能是 DSH 内的一个面板** |
| 独立性 | ✅ 独立应用，**能管 DSH 的生死**（自己 spawn `node … --profile <p>`、启动/重启/换版本） | — （它就是 DSH 自己） | ❌ 寄居在 DSH 里；**DSH 起不来时它也不在**；**换不掉自己脚下的进程** |
| 成熟度 | 22 个版本 / 6 周 / 30 篇 ADR / 约 27 篇独立验证报告 / 63,230 行代码 | 官方 | 0 |
| 一致性 | 自带一套 UI，与玻璃主题**不是一套材质** | 官方材质 | ✅ **与你的玻璃材质是同一套**（这是唯一的独占优势） |
| 你的实际可用性 | **0**（崩） | 可用但"不好看、不全" | 待建 |

### 7.2 本方案**真实**的价值点（只有三条，不夸大）

1. **它是唯一能"长在你现有材质上"的控制中心。** DSH Dock 的界面不可能变成你的液态玻璃；你要的是"界面是一套东西"，那只能自己做。**这是唯一一条不会被"官方以后补上"抹掉的优势。**
2. **它把 DSH 已经给你、但你没在用的官方接口变成看得见的东西。** 工作区的增删改、会话巡检、插件启停，官方接口**全都在**（见锚点 C）—— 现在只是没有入口。控制中心的价值，**80% 是"把已有的东西摆出来"**，不是"造新能力"。
3. **它的失败是可逆的。** 一个客户端插件的坏法上限是"面板打不开，删掉即恢复"；DSH Dock 的坏法是"启动即崩"和"窗口不能移动/缩放/关闭"。**在"出事了要好收拾"这个维度上，插件永远是更安全的选择。**

### 7.3 本方案**不**值得吹的地方（诚实清单）

| 常被吹的点 | 事实 |
|---|---|
| "替代 DSH Dock" | **替代不了。** 它有半张功能表（进程生命周期、DSH 版本切换、自更新、多平台）在插件的架构位置之外 —— 它自己 spawn `node … --profile <p>`，**插件换不掉自己脚下的进程**。控制中心能替代的最多是"**工作区 + 巡检 + 已装插件管理**"，**市场与系统控制台做不到** |
| "3400+ 插件市场" | **不做，也不该做。** 数据源不在我们手里；社区已有 `dsh-market`。请把它从方案 C 的期待里划掉 |
| "会话自愈，自动修好" | **不做。** 官方给的是 append-only 持久化 + `inspect` 只读巡检，**没有"改"的语义**。任何"自动修"都是自己写会话文件 = 丢对话风险 |
| "省时间" | **不一定。** 做最小版要 1.5~2.5 天，之后每天省下的是"切工作区多点两下"的时间。**它的价值主要在"出事时能看见、能救"，而不是日常提速** |
| "顺手就能做完" | **不能。** 对标一下量级：DSH Dock 是 **63,230 行代码 + 18,529 行文档**、22 个发行版、30 篇 ADR 的产物。本项目自己的记录也说明一切：写功能快（一组界面 1 轮），**找问题贵**（一轮审查挖出 21 条），而 8 类历史坑每类都是"看起来没生效"。控制中心是新的一批 DOM/API 触点，**必然复现同类成本** |

### 7.4 相对「就用 DSH 自带设置页」的价值点

**只有一个，而且是真的**：DSH 自带设置页是**官方 UI**，你改不动它的样子，它也**不会**把"工作区管理 + 会话巡检 + 插件救火"集中在一个你能随时打开、且长得像你界面一部分的地方。

**但反过来也要说清**：如果你的需求只是"改设置"，**自带设置页已经够用，做控制中心是纯浪费**。判断方法很简单 —— 打开 DSH 自带设置页看一遍，如果里面**没有你想找的东西**（工作区切换、会话健康、插件救火），那才轮到方案 C；如果有，**先别做**。
