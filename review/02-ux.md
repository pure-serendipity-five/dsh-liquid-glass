## 1. P0

### P0-1　全透明档 + 亮壁纸：正文/会话标题对比度 1.41–1.58:1，且「内容衬底」从未生效

**问题**
1. 六个玻璃面在 `glassTier:'off'` 下白纱 = 0（`client.js:92` → `client.js:386-391` → `client.js:435-455` → `client.js:402-409` 的 `REGION_MULT × 0`），玻璃感只剩 1px 描边/顶光/菲涅尔（`client.js:1449-1457`、`styles.css:60-87`）。
2. 文字被**强制成纯白**且「连写死颜色的元素也一起覆盖」：`textColor:'#ffffff'`（`client.js:259`）、`textColorAggressive:true`（`client.js:266`）→ 生成 `#root, #root * { color: #ffffff !important; }`（`client.js:1286-1299`）。
3. 兜底衬底**没有生效**：`contentFill:'glass'` 本意是给内容块铺一层 `rgba(255,255,255,0.06)`（`client.js:1330-1340`），但同一份样式里先写了
   `#root, #root *:not([data-dshlg-keep]):not([data-dshlg]):not([data-dshlg-region]) { background-color: transparent !important; }`（`client.js:1321-1328`）。
   `!important` 胜出、且两条规则命中同一批元素 → **`:where()` 那条白纱规则永远无效**，对话卡片/代码块/会话行下面什么都没有。
4. 剩下的唯一可读性手段是 `text-shadow`：`#root { text-shadow: 0 1px 2px rgba(0,0,0,.55), 0 0 2px rgba(0,0,0,.385) }`（`client.js:1277-1280`）+ 会话区 1px 描影（`client.js:1782-1789`）。阴影是**感知**手段，不改变 WCAG 对比度。
   **而且那层 1px 描影没落在正文上**：真机 DOM 实测里 `data-conversation-region` 只出现在**输入区**（`test/dsh-liquid-glass-diagnose.json:415`，元素 `D_tfqW_composerSeat`），整个 dump 里**没有 `data-conversation-scroll`** → `client.js:1782-1789` 的两条选择器只有 composer 命中。正文/会话标题实际只剩 `#root` 那层 2px 模糊衬影。**「正文可读性兜底」比设计意图少一层。**
5. 壁纸压暗只有固定 `dim: 0.15`（`client.js:320` → `#dshlg-wall::after`，`client.js:1400-1405`），且不随壁纸明暗变化。

**证据（量化）**——白字 `#ffffff`（L=1.0）对「壁纸 × (1−0.15)」的 WCAG 对比度：
| 壁纸平均亮度 | 压暗后 | 白字对比度 | 判定 |
|---|---|---|---|
| 纯白 #ffffff | 216.8 | **1.41:1** | 等于没有对比 |
| 浅灰照片 #f2f2f2 | 205.7 | **1.58:1** | 不可读 |
| 亮天空/雪景 ≈#dcdcdc | 187 | **1.92:1** | 不可读 |
| 中灰 #a0a0a0 | 136 | 3.55:1 | 仍不达标 |
| **#8b8b8b（临界）** | 118.6 | **4.50:1** | AA 门槛 |
| #808080 | 108.8 | 5.19:1 | ✅ |

即：**壁纸平均亮度高于约 #8B8B8B（55%）时，正文就跌破 WCAG AA 4.5:1**。本机壁纸库实测「60 张清单 / 18 张可用」，其中照片/场景类多数是亮调 —— 这不是边缘情况，是主路径。

**现有测试为什么拦不住这条**：验证台的对比度项明确写了「底色不是不透明纯色 → 合成色取决于背后壁纸 → **不判死**」，只打印「若背后纯黑/纯白 ≈ x:1」两个推断值（`test/verify.mjs:650-657`、`test/README.md:187-194`）；而全透明档位下六个面的 `background-color` 恰好都是透明 → **永远走 REPORT，不会 FAIL**。更麻烦的是 `test/README.md:196` 仍写着「插件 `CONFIG.textColor: ''`（跟随主题）」——**与实际不符**（`client.js:259` 是 `'#ffffff'` + `textColorAggressive:true`）→ 测试作者以为字色跟随主题，实际是强制纯白，等于连「推断值」都可能按错的字色算。

**影响**
用户（发动机标定工程师，日常要读长段中文技术内容）换成一张明亮照片壁纸后，会话标题与正文会**发灰发糊、长时间读很累**；而且他按 README 以为有「内容块极淡玻璃底」兜着（README 第 246-249 行也这么写），实际没有。这不是「用户主动选的取舍」本身，而是**取舍的兜底没生效**。

**建议**（按性价比排序）
1. **让衬底真的生效**：把 `client.js:1321-1328` 的结构清除规则收窄（例如排除 `[data-dshlg-content]` 或改用 `:where()` + 不带 `!important`），让 `contentFill` 的白纱能落地。（1 行级改动，风险低）
2. **衬底色要按背景明暗选，不要恒白**：亮壁纸下白纱会把白字衬得更白（更糟）。建议 `--dshlg-content-fill` 与 `--dshlg-content-ink` 成对派生：背景亮 → 黑纱 8–12%；背景暗 → 白纱 6%。可信的「背景明暗」来源有两条：
   - **无壁纸**：`readTheme()` 已经拿到 `theme.base` 与 `theme.dark`（`client.js:476-510`），直接算，不用采样；
   - **有壁纸**：壁纸 iframe 跨源读不到像素，但宿主 `/__preview` 图**带 `Access-Control-Allow-Origin: *`**（`index.js:136`，客户端已经在用它画缩略图，`client.js:3499`）。把它 `crossOrigin='anonymous'` 载入 → canvas → 求均值亮度，就能给每张壁纸算一个「压暗/衬底」档。**这正好把「读不到像素所以走保守值」这条已知局限变成可解**。
3. **给非程序员一个一键出口**：设置面板加两项 —— 「壁纸压暗」滑块（0–0.7，即时生效、localStorage 持久化）与一键「亮壁纸模式」（dim→0.55 或衬底→黑纱）。0.55 的压暗能让**纯白壁纸**也回到 4.76:1（可算），是成本最低的兜底。
4. 顺带把 README 第 157 行的 ⚠️ 换成人话（见 P2-8）。

**优先级**：P0（读不了字）

### P0-2　`prefers-reduced-transparency: reduce` 会把界面变成「白底白字」

**问题**
`styles.css:172-181` 在 reduce 档把玻璃面改成 **92% 白**
```css
@media (prefers-reduced-transparency: reduce) {
  #root [data-dshlg-region] { background-color: rgba(var(--dshlg-tone,255,255,255), 0.92) !important; ... }
}
```
而 `--dshlg-tone` 恒为 `255,255,255`（`client.js:1976` 定义、`client.js:2002` 写入 CSS，`styles.css:22` 兜底），同时文字被强制成 `#ffffff`（`client.js:259/266/1296`）。**白字压 92% 白底 → 约 1.06:1**。同行还有 `styles.css:404-408` 把 `.dshlg-bar` 也推到白系。

**同类问题（同一根因：底与字没有联动）**
- 预算降级：`styles.css:196-200` 把超预算浮层的底 `× 2.4`；`glassTier:'clear'`（0.368）时 = **0.883 白**，同样是白底白字。
- `contentFill` 的白纱固定是白色（`client.js:1335`）。
- 而 `reduced-transparency` 只覆盖 `[data-dshlg-region]`（side/right/approval/modal）+ `.dshlg-bar` + `.dshlg-brand`；**输入卡片 `.dshlg-glass`（六个玻璃面之一）、浮层 `[data-menu-material]`、以及本插件自制 UI（控制条/齿轮/圆点/面板/画廊）全都不覆盖** → 同一个系统偏好，5 个面变白、1 个面还是全透明，既不安全也不一致。

**影响**
Windows「设置 → 辅助功能 → 视觉效果 → 透明效果 = 关」（以及 prefers-contrast 用户）恰恰是最需要可读性的人群，结果是**整个左侧栏变成白底白字、什么都看不见**。这是本轮审查里破坏性最强的一条。

**建议**
1. 降级档的底不要写死白：按 `theme.dark` 派生（深色主题 → `rgba(13,17,23,0.92)` + 浅色字；浅色主题 → 白底 + 深色字），并且**同时**覆盖 `color`（用 `#root [data-dshlg-region] *` 一组 `!important`）。
2. 把 reduce 档补到 **6 个面 + 自制 UI**：`.dshlg-glass`、`[data-menu-material]`、`#dshlg-controls`、`#dshlg-gear`、`#dshlg-restore`、`#dshlg-settings`、`#dshlg-gallery`。
3. 预算降级 `×2.4` 同理：底白了就把字变深，或把降级底限幅到 ≤0.6。
4. 加一条自检：任何「底不透明度 > 0.5」的分支都必须同时给出深色 ink（可写成 CSS 变量对 `--dshlg-veil/--dshlg-ink` 一处派生）。

**优先级**：P0（可及性自毁）

### P0-3　控制条的「冰钻蓝白渐变 / 发光 / 内环」其实一条都没渲染出来

**问题**
`--dshlg-bar-tone` 在整个项目里**只在 `#dshlg-settings` 规则内定义了一次**（`client.js:2253`，注释还写着「壁纸控制条：蓝白玻璃」，是复制粘贴留下的），而它的使用方是**另一个元素** `#dshlg-controls`（`client.js:2369/2377/2378/2395/2396`）和控制条内的按钮（`client.js:2464/2472`），**且这些 `var()` 全都没有兜底值**。

CSS 自定义属性一旦未定义，`var()` 代入失败 → **整条声明在计算值阶段失效**（不是回落到上一行，是整条作废）：
- `background-image: linear-gradient(150deg, 白→#e0f2fe→rgba(var(--dshlg-bar-tone),.3)→#a5f3fc→白)`（`client.js:2366-2371`）→ `none`；
- `box-shadow: inset 顶光 + inset 5px 内环 + 两层蓝光晕 + 一层黑影`（`client.js:2374-2379`）→ `none`；
- `#dshlg-controls button` 的小宝石渐变（`client.js:2461-2465`）→ `none`；
- `button:hover` 的背景反馈（`client.js:2472`）→ 失效。

真正落地的只剩：`border: 1px solid rgba(186,230,253,.85)`（`client.js:2373`）、按钮的 1px 白描边（`2459`）、`opacity: 0.66`（`2388`）。
对照齿轮 `--dshlg-gear-tone`（`2214`）与圆点 `--dshlg-restore-tone`（`2421`）**都定义在使用方自己的规则里** → 只有控制条踩了这个坑。

**证据**
静态可判定（已 grep 全仓：`dshlg-bar-tone` 仅 2253 一处定义）。**待探针确认**：`ux-probe.mjs` 的 `out.bar` → `backgroundImage` 应为 `none`、`boxShadow` 应为 `none`、`toneVar` 应为空串。

**影响**
1. 用户看到的控制条 = 一根淡蓝描边 + 若干白描边按钮，`opacity 0.66`，**在亮壁纸下几乎看不见**；「冰钻蓝白渐变玻璃控制条」这个视觉承诺不存在。
2. 控制条是壁纸库的**唯一入口**（画廊按钮在它里面）→ 入口的存在感直接关系到可发现性。
3. 控制条的文字色是**近白粉** `#fff0f6`（深色主题，`client.js:2361`），压在亮壁纸上 ≈ 1.0–1.3:1，且**它自己是没有任何 text-shadow 的**（面板有、控制条没有）→ 「画廊 / 收起 / 松风」这些标签在亮壁纸下读不出。

**建议**
1. 把 `--dshlg-bar-tone` 提到 `:root`（`applyGlass` 里已经有一段往 `document.documentElement` 写变量的循环，`client.js:4235-4241`，加一行即可），并且给所有 `var(--dshlg-bar-tone, 125,211,252)` 补兜底值。
2. 控制条文字色按「背景明暗」选深/浅 ink（不要固定 `#fff0f6`/`#5b1236`），并补一层 `text-shadow`（面板已有的做法）。
3. 顺手把 `opacity 0.66` 的默认值提高（或在有壁纸时给底），否则描边再漂亮也压不住。

**优先级**：P0（核心控件不可见/不可读，且是一行级 bug）

### P0-4　设置面板「品牌文字」输入框：每敲一个字就丢焦点，等于不可用

**问题**
行渲染函数每次调用都整块重建：
`client.js:2922-2960` `paintSettings()` → `rows.replaceChildren()`（`2928`）→ 重新 `createElement('input')`（`2951-2956`）。
而文本输入的事件处理器是**每次 `input` 都调 `commitSetting`**：
`client.js:2895-2900` → `commitSetting()`（`client.js:2834-2841`）→ `saveSetting` + `applySettings` + `requestPass(true)` + **`paintSettings()`**。

于是：输入框在你刚敲下的那个字符之后被**从 DOM 移除**，新输入框是另一个节点 → 焦点掉到 `<body>` → 想敲第二个字符必须再点一次输入框。**「品牌文字」这个设置项实际上只能一次输入一个字符。**

**证据**
静态可判定（读代码即可确认节点被替换）。**待探针确认**：`ux-probe.mjs` 的 `out.typing` → `activeIsSameInput` 应为 `false`、`sameNode` 应为 `false`、`valueAfter` 会保留已存值但 `activeTag` 变成 `BODY`。
`test/settings.test.mjs` 只点了分段按钮、**从未向文本框输入**，所以现有 16 项全绿也覆盖不到这一条。

**影响**
用户改了品牌文字想打「Agent-枝星」四个字，会发现「打一个就跳走」，对非程序员来说大概率判成「这软件坏了」。同一路径还会**每个字符写一次 localStorage + 强制一整轮 pass**（`requestPass(true)` 绕过节流），有卡顿风险。

**建议**
1. `paintSettings` 改**原地更新**：分段按钮只切 `.is-on`；文本框仅在 `document.activeElement !== input` 时才写回 `value`，且不重建节点。
2. 文本输入改用 `change`/防抖（300ms）提交，避免逐字符持久化 + 全量重绘。
3. 给这一类「面板内的输入」补一条测试（`settings.test.mjs` 里加：focus → 连续 dispatch 两次 input → 断言 `document.activeElement` 仍是同一个 input）。

**优先级**：P0（设置项不可用）

### P0-5　「恢复默认」直接 `location.reload()`：无确认、无差别地丢掉界面现场，而且并不恢复全部状态

**问题**
`client.js:2888-2892`：
```js
if (btn.dataset.role === 'reset') {
  try { localStorage.removeItem(SETTINGS_KEY); } catch {}
  location.reload();
}
```
1. **没有二次确认**。对「非程序员 + 双击 bat 启动」的用户，误点即整页重载。
2. 重载会丢掉**界面现场**（正在输入的草稿、滚动位置、当前视图状态）—— 而这些与「外观设置」毫无关系。
3. **名为「恢复默认」却不完整**：只清了 `SETTINGS_KEY`（`client.js:48`），**没有清** `dshlg.pos`（拖动位置，`client.js:2996`）、`dshlg.controlsHidden`（控制条收起态，`client.js:3226`）、`dshlg.entry`（当前壁纸，`client.js:2116`）。用户点了「恢复默认」，控制条还是收起的、按钮还在他拖到的奇怪位置。
4. 与另一个按钮「重置位置」（`client.js:2877-2887`，只清 `dshlg.pos` + 摘内联样式）职责重叠、命名不互斥，用户无法预期二者差别。

**影响**
「恢复默认」是用户遇到问题的第一反应按钮，现在的行为是「静默重载 + 只修一半」。丢草稿是不可逆损失。

**建议**
1. 加一句人话确认：「恢复默认外观？会重新加载界面（正在输入的内容可能丢失）」，确认后再 reload。
2. 语义分层并写进按钮 title：

## 2. P1

### P1-1　控制条「可拖动」没有实现；拖圆点存下的位置从不写回控制条

**问题**
全仓 `makeDraggable(` 只有两处调用：**找回圆点**（`client.js:2625`，key `'bar'`）与**齿轮**（`client.js:2915`，key `'gear'`）。`#dshlg-controls` **从未**被接上拖动。
更矛盾的是：圆点用 `'bar'` 这个 key 读写位置（`client.js:2625`、`2633`），`ensureControls()` 建控制条时**从不调 `applySavedPos`**（`client.js:3242-3346` 通读无此调用）→ 用户拖完圆点，再点圆点恢复控制条，控制条回到 CSS 默认的 `left:18px; bottom:18px`（`client.js:2352-2353`），而圆点自己下次还出现在拖到的位置。**「位置记忆」只对圆点和齿轮生效，对控制条是假的。**

**证据**：`grep makeDraggable(` → 2625 / 2915；`grep applySavedPos(` → 2633（圆点）/ 2975（齿轮）/ 3014（定义）。
**待探针确认**：`ux-probe.mjs` 的 `out.dragBar` → `dshlgDrag` 应为 `null`、`moved` 应为 `[0,0]`。

**影响**
用户的既定决策里写明「控制条可拖动」，实际拖不动 —— 他会以为鼠标没抓稳，反复尝试。对「控制条挡住输入框」这个已知取舍来说，**拖动是唯一的手动解法**（自动避让默认关，见 P1-6），这条没实现等于那个取舍没有出口。

**建议**（二选一，别两头都不占）
- A（推荐）：给 `#dshlg-controls` 接 `makeDraggable(bar,'barBar')`，并把画廊的跟随逻辑挂到控制条上（现在挂在圆点上，`client.js:2625-2632`，而圆点只在收起态存在 → **那段画廊跟随代码实际是死代码**）；圆点改用独立 key（不叫 `bar`）。
- B：明确不做拖动，就在设置面板里把「控制条让开输入框」默认改成「自动上移」，并删掉拖动承诺与 cursor:grab（`client.js:229-230`、`3037`）。

**优先级**：P1

### P1-2　「找不回来」：设置里选「隐藏」不留找回圆点；齿轮位置不夹视口，可能跑到屏幕外

**问题（两条独立的丢失路径）**
1. **两条路径行为不一致**：
   - 控制条上的「收起」→ `setControlsHidden(true)` → 下次 pass 进 `controlsHidden()` 分支 → **建回圆点**（`client.js:3246-3251`）✅
   - 设置面板「显示壁纸控制条 = 隐藏」→ `commitSetting('controls','0')` → `CONFIG.wallpaper.controls=false` → 走 `client.js:3253-3257` 分支 → **只删控制条与画廊、直接 return，不建圆点** ❌
   用户感知是同一件事（「把控制条藏起来」），结果一个有找回入口、一个没有；而且这一路径下**画廊也一起消失**（画廊只由控制条里的按钮打开，`client.js:3334-3335`，设置面板里没有画廊入口）。
2. **齿轮不夹视口**：`positionGear()`（`client.js:2971-2989`）用 `gear.style.left = r.right + gap`（gap 默认 72，`client.js:98`），**没有任何 `innerWidth` 夹取**（对比 `applySavedPos` 是夹的，`client.js:3017-3020`）。控制条内容随壁纸名变长（`select max-width:150px`，`client.js:2485`）而变宽，窗口又可能被拖窄/半屏 → 齿轮被推到视口右侧之外。
3. 叠加：**控制条只在壁纸服务探到时才创建**（`passInner` 的 `wallActive` 门，`client.js:4199-4214`）。若宿主半体没起来（端口被占/没加载），此时用户既没有控制条也没有画廊；齿轮还在（`client.js:4228` 无条件调用），但它是「设置」而不是「壁纸库」，用户不一定会把两者联系起来。
4. 找回圆点位置在 CSS 里硬写 `left:132px`（`client.js:2407`，注释说是为了避开左下角的「枝星」/头像）→ 窗口很窄或侧栏宽度不同时会压在别的按钮上；且圆点的地址只在**创建那一刻**夹一次（`client.js:2633`），之后窗口缩放不再重夹（对比齿轮每次 pass 都会 `applySavedPos`）。

**证据**：`client.js:3246-3257`、`2971-2989`、`4199-4214`、`2407`、`2633`；`test/collapse.test.mjs:364` 只验了「收起后有点」，**没验设置面板那条隐藏路径**。
**待探针确认**：`out.hideViaSetting`（期望：`bar:false, dot:false, gear:true`）、`out.narrow`（期望 460px 宽时 `gearOffscreen:true`）。

**影响**
用户把控制条藏了以后**永久找不到壁纸库**（除非知道「⚙ 设置 → 显示壁纸控制条 → 显示」），而他正是为了「换壁纸/换场景」才装这个插件。这是产品最不该出现的失败模式（README 第 281-292 行自己把它列为「设计失误」，说明团队认可这条红线 —— 但只修了一半）。

**建议**
1. 两条隐藏路径**都留圆点**：把 `client.js:3253-3257` 的分支也调 `ensureRestoreDot()`（一行），或干脆把 `controls` 这个设置项从面板里去掉，只保留控制条上的「收起」（少一个状态源）。
2. `positionGear()` 加夹取：`left = Math.min(Math.max(18, r.right + gap), innerWidth - gearW - 6)`；若放不下，退到「控制条上方」或**把齿轮作为控制条的第 N 个按钮**（推荐 —— 免掉测量、免掉 gap 常量、窄窗也不会丢）。
3. 壁纸服务探不到时，在设置面板里给一行人话状态：「壁纸服务：未连接（宿主半体没起来）」，并把「显示壁纸控制条」的开关置灰；比什么都不说要好得多。
4. 圆点在 resize 后重新夹取（复用 `applySavedPos(dot,'dot')` 即可，key 独立）。

**优先级**：P1（唯一入口可能丢失）

### P1-3　「面板按背后亮度自适应」在真机上恒走保守分支；且存在一条会翻到 1.17:1 的分支

**问题**
`sampleBackdrop()`（`client.js:3134-3161`）用 `document.elementsFromPoint` 从栈底往上找第一个 `backgroundColor` alpha > 0.06 的元素。但：
- 壁纸层 `#dshlg-wall` 有 **`pointer-events:none`**（`client.js:1388`，iframe 继承）→ **根本不参与命中测试**，永远不在栈里；内置背景层同理（`client.js:1181`）。
- `buildBaseCss` 又把 `html, body, #root *` 的 `background-color` 全部 `!important` 清成 transparent（`client.js:1327`、`1361-1362`）。
⇒ 九个采样点全部落空 → `vals.length===0` → 返回 `{mean:0.5, spread:0, samples:0, unknown:true}`（`client.js:3157`）→ `needOpaque = true`（`client.js:3184`）→ 恒定走「0.6 厚底 + 深栗字」分支。
**这就是 Lead 实测 `对比度=4.89:1` 的来源**（4.89 恰好等于 `veil rgba(255,240,246,0.6)` 与 `ink rgb(74,13,43)` 按 `body=透明` 合成出来的值），而不是「按壁纸亮度算出来的」。
更细的一层：`sampleBackdrop` 里 `sawUnreadable` 只是被记进返回值 `opaque`（`client.js:3148/3160`），而 `adaptPanelReadability` **从未读 `opaque`**（`client.js:3184` 只看 `mean/spread/unknown`）。

**由此产生的一条危险分支（画廊开着时开面板）**
画廊是 z-index 同级、位置重叠的常驻面板（`client.js:2504-2507`：left 18 / bottom 74）。若画廊开着再点齿轮：
- 采样点会命中画廊的 `.thumb`（`background: rgba(0,0,0,.45)`，`client.js:2576`）→ 循环取 `relLuminance(0,0,0)=0`，**完全忽略 alpha**（`client.js:3152`），如实上报「背后很暗很匀」；
- `mean≈0, spread≈0` → `needOpaque=false` → `darkInk=false` → **veil 0.08 + 浅粉字 `rgb(255,208,230)`**（`client.js:3188-3192`）。
- 在亮壁纸上的合成对比度 ≈ **1.17:1**（可算：0.08×(255,170,205) + 0.92×205.7）。

**影响**
1. 「按实测亮度自适应」这个卖点没有真正工作 —— 它恒等于一个固定的厚底+深字，正好与「全透明」定调相反：**只有设置面板一块是 60% 不透明的粉白板**，和其它五个全透明面明显不是一套材质。
2. 用户按广告词理解的「面板会自己适应当前壁纸」不成立；换成亮壁纸时面板不会变。
3. 画廊+面板同开时面板会突然变成 1.17:1 的浅粉字，**正好在最需要看清设置的时候看不见**。

**建议**
1. **不要用 `elementsFromPoint` 猜背景**，用已知量：
   - 有壁纸 → 按 `/__preview` 图算的亮度（见 P0-1 建议 2）；拿不到就算「未知」；
   - 无壁纸 → `readTheme()` 的 `base/dark`（`client.js:476-510`）直接给。
2. **未知即保守**，并且让 `unknown` 与 `!bg.opaque` 都强制 `needOpaque`：`needOpaque = bg.mean>0.55 || bg.spread>0.3 || bg.unknown || !bg.opaque`（一行）。
3. 采样合成时要**带上 alpha**（`rgba[3]`），否则半透明黑 `rgba(0,0,0,.45)` 会被当成纯黑。
4. 面板视觉上向「全透明」靠：厚底只在真的需要时出现；底色可以由 `--dshlg-tone` 派生而不是固定 `[255,240,246]`，并去掉「粉字」这套遗留配色（见 P2-4）。

**优先级**：P1（含一条可达的 1.17:1）

5. 给控制条/齿轮/画廊加一个快捷键（例如 `Alt+W` 开合集），并在 README 里写一行。

### P1-5　品牌文字被清空后，官方字标**不会**回来（placeholder 与实现不符）

**问题**
`renderBrandLabel()`（`client.js:3924-3951`）**先无条件隐藏官方节点**
```js
for (const el of row.querySelectorAll('[class*="_brandMark"], [class*="_brandName"], ...)) {
  el.dataset.dshlgHidden = '1';
  el.style.setProperty('display', 'none', 'important');
}
let label = row.querySelector('.dshlg-brand-label');
if (!text) { if (label) label.remove(); return; }     // ← 只删自定义文字
```
而设置面板给这个输入框的 placeholder 是 **「留空 = 用官方字标」**（`client.js:2955`）。
⇒ 用户按提示清空 → 自定义文字被删、官方字标仍 `display:none` → **品牌区变成一片空白**，且没有任何恢复路径（除非在文本框里重新打点字）。
另外：`CONFIG.brand.label` 的注释也写着「设成空字符串则保留官方原始字标」（`client.js:205-206`），与实现不符。

**证据**：静态可判定。**待探针确认**：`out.clearLabel` → `customLabel:false`、`hiddenOfficial >= 1`、`officialVisible:false`。

**影响**
用户想「改回官方的样子」，按提示清空，结果左上角**什么都没有**了 —— 一个可逆操作的错觉。

**建议**：`if (!text)` 时把官方节点的 `display`/`data-dshlgHidden` 还原（并 `stripBrandPaint` 只作用于仍在显示的节点），或把 placeholder 改成「清空 = 不显示任何标识」。

**优先级**：P1（误导性文案 + 状态不可逆）

### P1-6　「控制条让开输入框」用错左边界常量（72 vs 实际 18），开了也可能仍盖住输入框；画廊不会跟着上移

**问题**
`avoidComposerOverlap()`（`client.js:2670-2711`）里 `const barL = 72;  // CSS 里的左边界`（`2694`），但控制条 CSS 是 **`left: 18px`**（`client.js:2352`）。横向重叠判据 `barL < cr.right && barL + barW > cr.left`（`2697`）因此整体右移 54px：
- 判定「右侧不重叠」偏晚/偏早都可能，实际后果是**输入框左半部分与控制条重叠时判不出重叠** → 开启自动上移后控制条仍压在输入框上。
另外画廊固定 `bottom:74px; left:18px`（`client.js:2506-2507`），**只有拖动回调才会跟着控制条走**（`2627-2632`，而那段挂在圆点上、是死代码，见 P1-1）→ 控制条自动上移后，画廊留在原位，两者分家/重叠。
`placementKey` 的去重逻辑（`2704-2707`）本身写得不错，能避免振荡。

**证据**：`2694` vs `2352`；`2506-2507`；`2625-2632`。

**影响**
用户在设置里主动开了「自动上移」（说明他已经被遮挡困扰），结果**仍然被遮** —— 比不给这个开关更伤信任。控制条上移后画廊压在输入框/控制条上，视觉混乱。

**建议**
1. 把左边界改成实测：`const barL = el.getBoundingClientRect().left`（同一函数里已经在读 `el.offsetWidth/offsetHeight`，顺手量 left 即可）。
2. 画廊位置改为「跟随控制条」的单一来源：抽一个 `placeGallery()`，在控制条上移/拖动/resize 后统一调用。
3. 加一条回归：开启 `barAvoid` 后断言 `barRect.bottom <= seatRect.top`。

**优先级**：P1

### P1-7　`prefers-reduced-transparency` 与「玻璃预算降级」都把底变白，却没有配套的字色（与 P0-2 同根，这里单列预算路径）

**问题**
`styles.css:196-200`
```css
[data-dshlg-glass-over] { backdrop-filter:none !important;
  background-color: rgba(var(--dshlg-tone,255,255,255), calc(var(--dshlg-alpha,0.08) * 2.4)) !important; }
```
`--dshlg-tone` 恒白（`client.js:1976`）。在 `glassTier:'clear'`（tint 0.08 × REGION_MULT 4.6 = 0.368）时降级底 = **0.883 白**；`regular`（0.138）= 0.33（可接受）；`off`（0）= 0（无影响）。
即：**用户在设置里把通透度调到「白纱 8%」+ 同时开 3 个以上浮层时，被降级的浮层会变成近白实底 + 强制白字**。
`GLASS_BUDGET = 2`（`client.js:4323`）与 README 第 60/153 行写的「≤3」不一致（文档漂移，见 P2-8）。

**影响**

## 3. P2

### P2-1　自制 UI 的「退出/关闭」通道不完整
- 画廊 head 只有标题与计数，**没有关闭按钮**（`client.js:3572-3574`）；点开画廊后要么再点一次控制条里的「画廊」，要么点卡片换壁纸（**换完不自动收起**，`3539-3543`）。画廊最大 `760×560`（`2509-2510`），会盖住大半个界面。

### P2-2　切壁纸后不重算面板自适应 / resize 后圆点不重夹
- `adaptPanelReadability()` 只在**开面板时**（`client.js:2854`）与**窗口 resize 时**（`4399`）调用；换壁纸（`onControlCommand('wallpaper')`，`3851-3864`）不调用 → 面板开着时换壁纸，厚度/字色停留在旧壁纸的判断上。
- 找回圆点的位置只在创建时夹一次（`2633`），窗口缩放后不重夹（齿轮每次都夹，`2975`）。
- **建议**：换壁纸后 `requestAnimationFrame(() => adaptPanelReadability())`；圆点复用 `applySavedPos` 在 pass 里兜一次。
- **优先级**：P2

### P2-3　「通透度」不影响自制 UI，用户会以为开关坏了

**建议**：要么让自制 UI 也吃档位（同一套 `--dshlg-alpha`），要么在设置行下加一句「只作用于侧栏/输入栏/浮层」。

## 4. 如果只能改三件事，改哪三件

### 第 1 件：把「亮壁纸 = 读不了字」这条根修掉（P0-1 + P1-7）
- 内容：①修 `client.js:1321-1340` 的层叠冲突，让衬底真的生效；②衬底色随背景明暗（亮 → 黑纱，暗 → 白纱），不再恒白；③用宿主 `/__preview`（`index.js:136` 已带 `ACAO:*`）估壁纸亮度，给出自适应 `dim`；④设置面板加「壁纸压暗」滑块 + 一键「亮壁纸模式」。
- **取舍理由**：全透明是用户定调，不能推翻；但「壁纸完整透出」与「白字读得出」在亮照片壁纸上是**数学上不可同时满足**的（纯白壁纸 1.41:1）。唯一出路是让「压暗/衬底」这条路真的可用，并且**把选择权交给用户**（滑块 + 一键），而不是让他去改 CONFIG。不做这一件，插件在用户最常用的那类壁纸上就是不可用的；做了这一件，其余问题都还有绕法。

### 第 2 件：把「底」和「字」绑成一个决策（P0-2 + P1-7 + P2-4）
- 内容：引入成对的 `--dshlg-veil / --dshlg-ink`（或 `data-dshlg-fit="dark-ink|light-ink"`），所有「把底变白/变厚」的分支（reduced-transparency 92%、预算降级 ×2.4、contentFill 白纱、面板自适应）都必须同时决定字色；同时把 reduce/contrast 两档补到 6 个面 + 自制 UI；顺手删掉遗留的粉字。
- **取舍理由**：这是本轮唯一「系统性」的隐患 —— 白底 + 强制白字一旦同时发生就是白纸黑字失效（而且触发它的是**系统辅助功能开关**，用户完全不知道自己按了什么）。补丁式修法（只改 92% 那一处）会在下次有人调 `--dshlg-tone` 或加降级档时复发；成对派生是一次性投入、永久止血。代价是改动面比看起来大（要碰 `buildBaseCss`/`buildRegionCss`/`styles.css` 三处），所以必须和第 3 件分开做，别混在一次提交里。

### 第 3 件：让自制 UI「看得见、改得动、丢不了」（P0-3 + P0-4 + P0-5 + P1-1 + P1-2）
- 内容：①`--dshlg-bar-tone` 提到 `:root`（`client.js:2253`）+ 全部 `var()` 补兜底 → 让冰钻控制条真的出现；②`paintSettings` 原地更新（修输入框丢焦点）；③设置里的「隐藏」也留找回圆点 + 齿轮夹视口（或把齿轮挪进控制条当按钮）；④「恢复默认」加确认、清全状态、保留壁纸选择；⑤要么真的给控制条接上拖动，要么删掉承诺、默认打开自动避让。
- **取舍理由**：这五条都是**一行到十行级、零架构风险**的修补，但每一条都直接决定「用户能不能用」：控制条是壁纸库唯一入口（不可见/不可拖/可能跑出屏幕），设置面板是唯一的自救通道（文本框打不了字、「恢复默认」乱来）。相比重做材质或改探测架构，这一件的**投入产出比最高**，而且可以在第 1、2 件之前先单独发一版。
- 明确**不做**：不推翻「全透明 + 1px 描边」的定调（只在其上加兜底），不重做整套调色（只把墨色改成按背景选择），不试图读跨源 iframe 的像素（改用宿主 `/__preview`），不动 Wallpaper Engine 兼容那一摊。
